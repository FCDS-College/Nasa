## 0. The served RAG pipeline in one picture

```
INGEST   PDF → PyMuPDF text, OCR when blank/garbled → normalise (NFKC, de-hyphenate, headers) → 1 chunk = 1 page
         HTML/JSON/ISA-Tab → 1 chunk = 1 section;  PSI tables → experiment rows (lexical only, no vectors)
         → tsvector (search_tsv, search_tsv_keep) · bge-small embedding of the first 2,000 chars (page mode)
           or 1,200-char windows (window mode, off) · NLP records + graph edges (not used by retrieval)

SEARCH   query → rule rewrite (dense only) → lexical (AND by default; OR+IDF off) top ≥200
                                           → dense ANN top 10, sim ≥ 0.55, filters applied afterwards
         → RRF k=60 → cross-encoder over the first 10 (first 2,000 chars of each page) → page

CHAT     search(question) + search(each of ≤5 longest words)  → merge by hit count → ≤6 passages
         → document passages: best 1,200-char window of the page; experiment passages: test id + fuel only
         → router (structured JSON, temperature 0, evidence in a fenced user message)
         → drop citations not supplied → numeric traceability check (warn) → in-process cache (1 h)
```

## 2. New findings

Severity: **High** (wrong or unsafe output a user can see), **Medium** (quality or cost defect), **Low** (latent, or matters only after a planned change).

### N1 Rejecting evidence does not stop cached chat answers from citing it (High, Repro)
- **Where.** `admin.py:214` `review_evidence` changes `review_status` and commits. It neither publishes a knowledge version nor touches the answer cache. The cache key is the knowledge version (`main.py` `chat`), and entries live 3,600 s (`cag.py:24`).
- **Reproduced.** Ask a question → answer cites `E`. `PUT /api/admin/evidence/E/review {"rejected"}` → `/api/search` no longer returns `E`, but the same question returns `cache_hit: true` with `E` still in `sources`.
- **Impact.** Breaks the documented rule "Rejected evidence is never retrieved or cited" (ADMIN_DATA_OPERATIONS procedure 7) for up to an hour on every API process.
- **Fix.** On a review change, either publish a new knowledge version (`trigger="review"`, e.g. `corpus-<digest>+review-<audit_event_id>`) or evict cache entries whose `sources` contain the evidence ID. The first is simpler and also invalidates the investigations cache. Add the reproduction as a regression test.

### N2 Chat cannot use the flight-test tables: experiment passages carry no measured values (High, Repro)
- **Where.** `main.py:737` `_passage` turns an experiment hit into `"Experiment FLEX 123: fuel or material n-heptane; gravity regime microgravity."` The table cells (O₂, pressure, diluent, outcome), which are in `experiment.searchable_text` and in `experiment_condition`, never reach the model. The reranker sees the same value-free text (`_experiment_text`). The cited `evidence_id` is the experiment's *first* non-rejected condition, not the cell that matched.
- **Impact.** The question this product exists for ("what happened at 21 % O₂ and 1 atm?") cannot be answered from the 840 flight tests through chat. A model either says the evidence is insufficient or answers from priors; any number it gives is then flagged by the support check, because no passage contains one. The dashboard insights have the data; chat does not.
- **Fix.** Render experiment passages from their conditions, e.g. `FLEX test 123 (n-heptane): O2 0.21 mole fraction; pressure 101.3 kPa; diluent N2; outcome radiative extinction`, cite the condition evidence IDs that the passage contains (one passage, several IDs, or one passage per cited cell), and use the same text for the reranker. Add an evaluation question per investigation that needs a table value.

### N3 The reranker and the LLM read different parts of a page (Medium, Code)
- **Where.** `main.py:621` hands the reranker `chunk.text`, which `cross_encoder.py` cuts at 2,000 characters; 71 % of pages are longer (NLP audit R-5). Generation reads `best_window(page, question)`, which for about half the gold questions begins after character 400 and for 19 % after 2,000 (NLP audit G-1).
- **Impact.** The reranker scores a page on text the model will not read, and cannot see evidence that lies past character 2,000. This may explain why the reranker's gain is not measurable.
- **Fix.** Rerank on `best_window(chunk.text, query)` (cheap, pure Python). Then re-run the benchmark with the bootstrap intervals.

### N4 Chat sub-queries drop chemistry tokens and pick the longest words (Medium, Repro)
- **Where.** `main.py:728` `_question_terms` keeps tokens of 3+ characters and the five *longest*. For "Does O2 concentration change extinction of n-heptane droplets in He diluent at 1 atm?" it searches `concentration, extinction, n-heptane, droplets, diluent`: `O2`, `He` and `atm` are lost. `evidence_window.question_terms` keeps 2-character tokens, so the two term pickers disagree.
- **Fix.** Use `question_terms` (or `lexical_query.query_terms`) and rank by document frequency (the IDF already cached by `lexical.py`), not by length.

### N5 No retrieval-side abstention: any lexical hit goes to the model (Medium, Code)
- **Where.** `main.py:845` abstains only when *nothing* matched. A question that shares one common word with the corpus ("flame", "oxygen") always reaches generation with six passages, however weak. The composer's abstention logic exists only in the unserved library.
- **Impact.** Refusal depends entirely on the model obeying "say so plainly". Unanswerable in-domain questions are exactly where the NLP audit found dense scores give no signal (R-2).
- **Fix.** Gate generation on the best reranker logit (or a fused score) with a threshold calibrated on the 11 unanswerable drafts once verified; return `insufficient_evidence` with the passages, as the degraded path already does. Until calibrated, log the score with each answer so the threshold can be fitted.

### N6 One chat question costs up to six full searches (Medium, Code)
- **Where.** `_retrieve_passages` calls the HTTP handler `search()` up to 6 times. Each call runs 2 `COUNT` queries, `index_status` (3 more `COUNT`s), one query embedding, a deep-rank window query when dense adds hits, and a cross-encoder pass over 10 pages (about 0.7 s on CPU each, [retrieval-2026-11-12.md](../evaluation/reports/retrieval-2026-11-12.md)).
- **Impact.** Several seconds of CPU per uncached question, most of it spent on totals and pages nobody sees. Chat latency is not measured anywhere (no p50/p95).
- **Fix.** Factor candidate generation out of the handler (`_candidates(plan, filters, limit)` without counts), gather candidates for all sub-queries, fuse them once with RRF (one list per sub-query), and rerank the union once. Cache `index_status` per knowledge version.

### N7 The chat merge is ad hoc (Medium, Code)
- **Where.** `main.py:751`: passages sort by "number of sub-searches that returned them", then by `position * 10 + rank`. The full-question search counts the same as a single word; reranker scores are thrown away; `rank` beyond 10 collides with the next sub-query's band.
- **Fix.** Part of N6: RRF across sub-query lists (the stack already implements it), optionally weighting the full question higher, then one rerank.

### N8 A changed source file leaves its old chunks and evidence searchable (Medium, Repro)
- **Where.** Chunk and evidence IDs include the file's SHA-256 (`ingest.py:197`); the document ID does not. `_drop_stale_page_chunks` (`ingest.py:228`) only removes pages that disappeared and embeddings of changed text, matching by page number, so the old version's chunk for a page that still exists is kept. HTML, JSON and ISA-Tab documents (`ingest.py:420`, `:503`) have no stale-section cleanup at all.
- **Reproduced.** Store page 1 under hash `a…`, change the file record's hash to `b…`, run the drop-and-store sequence: the document now has two chunks for page 1, `aaaa…:v1:1` (old text) and `bbbb…:v1:1` (new text), both citable.
- **Impact.** Latent today (the committed corpus is fixed), certain on the first NTRS or PSI file update: duplicate or superseded passages in search, chat and the graph.
- **Fix.** Delete every chunk and passage evidence of the document whose ID prefix is not the current file hash (keeping human reviews by locator, as `_keep_review` does), and apply the same rule to section documents. Add the reproduction as a test.

### N9 The `domain=combustion` filter is skipped for dense-only hits (Low, latent, Code)
- **Where.** `main.py:600`: the query that loads dense hits outside the lexical list applies `source_id`, `experiment_id` and rejection filters, but not `combustion_sources`. Latent because the only non-combustion source (DSI) is not ingested.
- **Fix.** Add `.filter(DocumentChunk.source_id.in_(combustion_sources))` when `domain == "combustion"`; add a test with a non-combustion chunk.

### N10 Window mode uses a partly built window index without warning (Low, latent, Code)
- **Where.** `main.py:580` calls `search_window_chunks` whenever `FLAME_DENSE_GRANULARITY=window`; it falls back to the page index only when the window table is empty. `window_index_status` (which reports `stale`) is never consulted, so pages without windows silently drop out of the dense leg.
- **Fix.** Use the window index only when `window_index_status(...)["state"] == "up"`, otherwise the page index, and report which was used in `retrieval`.

### N11 Dense hits are filtered after the ANN cut (Low, Code)
- **Where.** `search_chunks` takes the global top 10 and filters afterwards. With a `source_id` or `experiment_id` filter the dense leg usually contributes nothing. HNSW `ef_search` is left at the pgvector default (40).
- **Fix.** Over-fetch when filters are present (e.g. 100), or filter inside the vector query (join on `document_chunk`) and set `hnsw.ef_search` per query.

### N12 The vector index version is not unique (Low, Code)
- **Where.** `vector_index.py:158`: `bge-small-en-v1.5-<rows>-<YYYYMMDD>`. Two builds on one day with the same row count but different text get the same name; `publish` treats the second as already published. The manifest then names two different index states with one version, which weakens the provenance of `retrieval.index_version`.
- **Fix.** Derive the version from a digest of `(chunk_id, sha256(text))` over the embedded rows, as `_publish_corpus_version` does for files.

### N13 The answer-cache key omits retrieval configuration (Low, Code)
- **Where.** `answer_cache.make_key` includes knowledge version, prompt, mode and reranker, but not `STACK_VERSION`, `lexical_mode`, `dense_granularity`, the evidence-window parameters or `answer_support_check`. Harmless while the cache is per process (a config change restarts it); wrong once the planned shared (Redis) cache exists. Normalisation is case and whitespace only, so the hit rate is probably low (unmeasured).
- **Fix.** Add a `retrieval_config` digest to the key before moving the cache to Redis; record the hit rate in `/api/health`.

### N14 Experiments and pages are fused on unrelated scales (Low, Code)
- **Where.** Experiment hits get one list (`experiment_lexical`), pages up to two (`lexical`, `dense`), and RRF adds them with equal weight. A page found by both legs always beats the best experiment, and with 840 rows sharing investigation names, experiment lists are long and flat. No benchmark question needs a table row, so the effect is unmeasured.
- **Fix.** Decide after N2, with table questions in the gold set: separate quotas per result type in chat, or per-list RRF weights.

### N15 Large unserved RAG library; NLP and graph data unused at query time (Medium, structural, Code)
- **Where.** The API imports from `ai.rag` only `search_stack`, `evidence_window`, `verification.support`, `query.rewrite` (via the stack), `cache.cag`, `ingestion.{normalize,windows}`, `retrieval.{aggregate,lexical_query}` and `nlp`. Not served: `service.py`, `retrieval/{rag_retrieval_pipeline,hybrid_search,vector_search,keyword_search,metadata_filter,fusion}.py`, `generation/composer.py`, `context/context_builder.py`, `citations/citation_manager.py`, `memory/session_mag.py`, `prompts/registry.py`, `embeddings/embedding_service.py`, `reranking/*` (sentence-transformers), `ingestion/{chunker,pdf_loader,pipeline}.py`. Docs under `docs/ai/` describe several of them as the pipeline.
- **Impact.** Two retrieval stacks with different thresholds (0.55 vs 0.7), score scales (logits vs sigmoid) and behaviour (P-2), and a reviewer cannot tell which is real. Meanwhile the knowledge graph (951 entities, 10,683 cited edges) and the D1 NLP records, which could answer condition questions, are not used by search or chat.
- **Fix.** Move unserved modules to `ai/rag/legacy/` (or delete them) with a README pointing at the served path; port the one idea worth keeping (composer abstention) into the API as N5. Treat graph-assisted retrieval (entity → experiments → condition evidence) as the follow-on to N2.

### N16 The generation path has never been evaluated end to end (High for claims, Doc)
- **Where.** `FINAL_ARCHITECTURE.md`, the production-readiness roadmap (EV-08, EV-11) and the NLP audit all note it: no faithfulness, citation precision or abstention number exists for `/api/chat` with a real model; the unsupported-claim gate row has no code.
- **Fix.** Verify the 35 passage drafts (`python -m ai.rag.evaluation.adopt_drafts` after the verification sheet), then run `/api/chat` over them with a local model and report citation precision, abstention on the 11 unanswerables, support-check flags and latency. Until then, answer quality should not be claimed.

## 4. What is sound

- One served ranking stack with deterministic RRF and exact paging; reranker failure degrades to the fused order and is reported.
- Strong provenance: stable IDs, page/section locators, evidence rows for every passage, citation filtering to the supplied set.
- Evidence is escaped and sent as data; output is schema-validated inside the routed call, so a bad provider counts as a failure.
- Degraded modes are explicit (`generation_unavailable`, `CHAT_UNAVAILABLE`, `reranking.status`), and degraded answers are not cached.
- Offline-first routing with embedding-model identity checked against the index.
- The team's own evaluation reports state their limits honestly (bootstrap intervals, AI-authored questions).

## 5. Known limitations of this audit

- PostgreSQL-only paths (`or_idf`, window index, pgvector) were read, not executed; CI covers them.
- No language model was run, so no answer-quality numbers are given; N5 and N16 are about missing controls, not measured failures.
- Latency in N6 is estimated from the committed reranker timing, not measured.
