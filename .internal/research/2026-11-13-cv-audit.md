## 2. Findings (most severe first)

### CV-1 Critical: the served video pipeline reports telemetry text and cabin hardware as flames (V-run)

`cv/video_analysis.py:128-129` passes every full frame to the image segmenter. The BASS-II flight videos carry a white telemetry overlay (`FUEL AIR FAN RAD` plus a date line) in the top ~17% of the frame. White text on black is the highest-contrast "bright blob" in the frame, so Otsu picks it.

Measured on the three committed BASS-II samples (`sample_every=30`, up to 60 frames):

| Video | PRESENT | Box is the overlay text | What is actually segmented |
|---|---|---|---|
| `TEST_P12_LOS_Portion` | 59 / 59 | **59 / 59** | Only overlay glyphs (`RAD`, `FUEL`). There is no flame. |
| `TEST_B1` | 45 / 45 | 23 / 45 | The real flame mid-burn; overlay text before ignition and after extinction |
| `TEST_T25_2ND_VIEW` | 60 / 60 | 0 / 60 | The blue glovebox floor and cables of a cabin camera view. There is no flame. |

The false detections have confidence 0.62–0.99, above the 0.60 `PRESENT` threshold. See `cv-audit-assets/video-overlays.jpg`: one row per video, showing the first, middle and last sampled frames.

**The demo is affected.** `infrastructure/demo/submit_demo_analyses.py:26-27` submits `TEST_B1` with `sample_every=15, max_frames=120`. Reproduced exactly: 90/90 frames are `PRESENT` with `persistenceRate = 1.0`, but **46 of the 90 (51%) are the overlay**. The real flame appears only in roughly frames 330–1095. The overlay's median area (2,954 px²) is close to the flame's (3,184 px²), so the "flame area over time" chart in `DEMO_RUNBOOK.md:153` looks plausible and hides the error. The API stores the result with `"classification": "measured"` (`apps/api/flame_api/worker.py:456`) and the observation "Brightness-based CV detected a flame in 90 of 90 sampled frames" (`worker.py:461`).

The team already knew about the overlay: `cv/video_training.py:23` masks the top 20% (`BANNER_ROWS`) so the ResNet cannot read it. The production video path has no equivalent mask.

`FINAL_PROJECT_STATUS.md:29` lists "Image and video CV through the API (BASS-II flight video, SPICE photos)" as **COMPLETE**. That status is not supported for video.

**Fix:** add a per-source static exclusion mask (overlay ROI), applied to the frame before segmentation and recorded in the config digest. Also reject components whose box is static across many frames (overlays and hardware do not move; flames do). Then add a regression test on one real BASS-II frame that asserts the box is not in the overlay region.

### CV-2 High: detection score passes saturated, unstable and background-less masks as PRESENT (V-code, V-run)

`cv/flame_cv.py:771-784`:

- **Bug.** When the mask covers the whole content area, `outside_sel` is empty, `outside_mean` defaults to `0.0` (`:774`), and contrast becomes the maximum (255). Run on `FF-PSI-69/C021H03C_00216` (a fully saturated white frame), the result is `PRESENT` at 0.80 with `segmenterConfidence = 0.0` and the `blur`, `saturationClipping` and `occlusion` flags all true. An empty background should make contrast not estimable, which should give `UNCERTAIN`.
- **Area term saturates at 0.2% of the frame** (`area_frac / 0.002`, `:782`). Any blob above about 0.2% gets the full 0.3. Contrast ≥ 72 gray levels gives another 0.3, so the total reaches 0.6 (`PRESENT`) **with zero stability**. This is how overlay text passes.
- **Quality flags never feed back into status.** A mask flagged blurry, clipped and occluded can still be `PRESENT`.
- **Hard-coded confidences** (`:810`, `:814`: `det_conf = 0.9` for ABSENT). This contradicts the file's own rule, "every confidence / flag is computed, never hard-coded" (`:9`).
- `scientificInterpretation.classification` is always `"MEASURED"` (`:886`), even when nothing was detected.

Still images across all committed samples (V-run, `cv-audit-assets/still-overlays.jpg`):

| Set | Result |
|---|---|
| SPICE (FF-PSI-107) | 20 / 20 `PRESENT`. Luminous flames are segmented cleanly; this is where the method works. |
| FLEX (FF-PSI-69) | 95 PRESENT / 24 UNCERTAIN / 1 ABSENT. Several PRESENT masks are a glowing hardware arc at the frame edge or a saturated frame. |
| SAFFIRE (FF-PSI-98) | 30 / 30 `UNCERTAIN`. The masks follow the monitor bezel. |
| DSI | 10 PRESENT / 2 UNCERTAIN. Some masks are particle texture. |

### CV-3 High: the evaluation cannot measure the failure modes above (V-code)

- `cv/contracts/evaluation_report.json` and `docs/cv/evaluation-report.md` cover 10 SPICE images from **one** experiment. All of them contain a flame, so the evaluation has **no negatives** and false positives (CV-1, CV-2) are invisible by construction. It has no ground-truth masks, and it was run on pipeline **v1.1.0** while v1.2.0 is served.
- `docs/cv/evaluation-report.md` and `cv/models/otsu-contour-baseline/MODEL_CARD.md` contain `[cite: 7]` tokens, which are leftover LLM citation debris.
- None of the 67 CV tests that run without torch uses real flight media (the 8 OCR tests use synthetic inputs too). All `flame_cv` and video tests use synthetic ellipses (`make_synthetic_flame`), which match the method's assumptions exactly.
- `run_cv_evaluation` (`flame_cv.py:986`) is sound (group-aware notes, IoU/F1, null acceptance threshold). It has simply never been given ground truth.

**Fix:** build a small labelled set: about 60 frames, split by test, with at least 30% no-flame frames (pre-ignition, post-extinction, cabin views), and include overlay frames. Report detection precision and recall, plus IoU on the PRESENT frames. Grade every change to CV-1 and CV-2 against it.

### CV-4 High: `docs/cv/performance.md` describes hardware behaviour the code does not have (V-code, V-run)

The page reports NVIDIA L40S VRAM use (1.2–2.1 GB), a "3.5× slower on CPU" ratio, recommended batch sizes of 16–32 and vLLM co-existence limits. The pipeline is CPU OpenCV/NumPy. `opencv-python-headless` has no CUDA path, and the code does no batching. Measured on CPU: **p50 37.5 ms, p95 52.4 ms** per 720×480 frame (40 frames), so the latency line is roughly right and the GPU section is unsupported. Remove the GPU section or label it as planned.

### CV-5 Medium-High: temporal metrics are largely not estimable at API defaults, and flicker is the wrong physics for microgravity (V-code)

- The API default is `DEFAULT_SAMPLE_EVERY = 30` (`apps/api/flame_api/analysis.py:28`), which is 1 Hz at 29.97 fps. Flicker requires `sample_every = 1` (Nyquist guard), and tracking requires a sampling interval of 0.5 s or less (`worker.py:424-427`). At defaults, only persistence and area-change rate are reported, and CV-1 corrupts both.
- The flicker band is 0.5–10 Hz (`temporal_analysis.py:25,28`). Flame flicker in that band is a buoyancy instability. Microgravity flames do not flicker that way, so a "dominant frequency" of the mask area is more likely threshold jitter or camera noise. The guards (Nyquist, run length, peak/median ≥ 15) are well designed, and `docs/cv/temporal-analysis.md` admits the metric is unvalidated.
- Each frame gets its own Otsu threshold, so frame-to-frame threshold changes add area noise that the temporal metrics then read as flame dynamics. A per-video threshold, or a hysteresis band, would separate the two.

### CV-6 Medium: the CNN transfer-learning result is underpowered and partly mis-reported (V-code; numbers read from the committed reports)

`cv/video_training.py` is the most methodologically careful piece of ML in `cv/`. It uses leave-one-test-out grouping (views of one test share a group), inner group-CV for regularisation, a trivial baseline per task, and overlay masking against identity leakage. Remaining problems:

- **n = 17 videos, 15 tests, no intervals.** Initial-O₂ MAE 1.876 (ResNet18) vs a 2.303 baseline has no CI or permutation test. With 17 points it is not distinguishable from noise. The baseline uses the full-sample mean, which includes the held-out item. That makes the baseline slightly optimistic, so the reported gain is conservative, but the protocol is inconsistent.
- **Backbone selection on the test folds.** ResNet18 and ResNet50 were both run and evaluated with the same LOTO folds (`training_report.json` vs `training_report_resnet50.json`). ResNet50 is worse on O₂ (2.135) and better on fuel (0.294). Picking a backbone from these folds is a test-set choice.
- **Fuel-family classification is ill-posed.** 6 classes, mostly singletons, so held-out classes are unseen at training time. All three models score at or below majority (0.353 / 0.235 / 0.294 vs 0.353). Unlike the regression task, the report has no `beatsBaseline` field for this task, so the failure is not flagged.
- ImageNet ResNet on 224×224 squashed frames (aspect ratio not kept), mean/std pooling over 64 frames. This is reasonable as a frozen baseline.
- ImageNet weights download at run time (`weights="DEFAULT"`) and are not in `cv/configs/offline_manifest.json`, so this path fails in offline mode.

### CV-7 Medium: the self-supervised temporal head reports its model-selection score as its result (V-code)

`cv/video_embedding.py`: early stopping picks the epoch with the best **validation** MSE (`:93`) and returns that same number as `val_mse` (`:103`). There is no held-out test segment, so `beats_baseline` (0.959 vs 2.131 copy-previous in the notebook) is optimistically biased. Normalisation statistics are also computed over the whole sequence, validation included (`:77`). Split into train, validation and test segments in time order, and normalise using train statistics only.

### CV-8 Medium: the CNN, PINN and notebook "models" are scaffolding that report success (V-code)

- **`cnn_pipeline.py`:** `run_cnn_pipeline` (`:101-121`) never builds, loads or trains a model. It counts files and returns `"status": "SUCCESS"`. The split is a random per-image shuffle (`:22-34`), which contradicts the repo's own rule "split by test, never by frame" (`cv/README.md:36`). The binary head is `Dense(2, sigmoid)` with `binary_crossentropy` (`:64,68`), which is shape-incompatible with the integer labels from `image_dataset_from_directory` (it needs `Dense(1)`). There is also no class-folder dataset in the repo to train on.
- **`pinn_pipeline.py`:** a generic 1-D heat equation on [0,1]² with an arbitrary α=0.01. It has no initial or boundary conditions and nothing in the repo calls it or provides data. It also returns `"SUCCESS"`.
- **`cv/videoCNN/models.ipynb`:** the "PINN" loss is `0.01·mean(|p₀ − p₁|)`, which encodes no physics. Every target is the constant `[1.0, 0.5]`, and training and testing use the same single video. The notebook also contains hard-coded Windows user paths and a `pip install` of a package that does not exist (`openai-subprocess`).
- **Dependency cost:** the root `requirements.txt` pulls in **TensorFlow** solely for F and G. PyTorch and torchvision, which D and E need, are declared nowhere in the CV extras (CI installs torch separately for RAG).

Recommendation: either delete F, G and H, or move them to `cv/experimental/` with a README that says so, and take TensorFlow out of the root requirements.

### CV-9 Medium: telemetry OCR is unevaluated and uncalibrated (V-code)

`telemetry_ocr.py` is a clear improvement on the three divergent notebook extractors. Those gave inconsistent readings of the same video (`fan=144` vs `fan=-20`), which justified the rewrite. It adds range validation and majority voting. However, `rois` defaults to `None` (`:26`) and the digit whitelist applies only in ROI mode (`:65-67`). The committed run returns `None` for every field, and no hand-labelled truth exists, so `field_accuracy` has never run. OCR is the obvious route to labels for D, and to the overlay mask for CV-1: the ROIs found for OCR are exactly the regions to exclude from segmentation.

### CV-10 Medium: HF Space integration risks (V-code; the health issue is Hyp)

- **Health probe path (Hyp, likely).** `HfSpaceCvProvider.health` requests `{base_url}/` (`ai/providers/cloud/hf_space_cv.py:138`), but the Space serves only `/health` and `/api/analyze`, with docs disabled (`cv/hf_space/app.py:15`). If the Space returns 404 at `/`, the router marks it `health_down` (`ai/routing/router.py:162`) and always falls back to local. Check this against the live Space.
- **Remote results are trusted.** The client checks only that three sections are dicts. It does not validate the payload against `AnalysisResult` or check that `pipelineVersion` matches the local version. The Space image copies `flame_cv.py` at build time, so an un-rebuilt Space silently serves a different pipeline version.

### CV-11 Low: hygiene (V-code)

- `cv/README.md:8-28` contains **unresolved merge-conflict markers** (`<<<<<<< HEAD` … `>>>>>>> Princess`).
- `tests/cv/test_telemetry_ocr.py:2` does an unconditional `import torch`. Without torch, **collection of the whole `tests/cv` directory fails**, not just that file. Use `pytest.importorskip("torch")`.
- The `flame_cv.py` docstring says v1.1.0; the code is v1.2.0.
- Artefact names derive from the file stem (`{stem}_processed.png`, `{stem}_mask.png`). In batch use, `X.jpg` and `X.png` overwrite each other's artefacts, and `_artifacts_exist` checks existence, not checksum. The API path is safe because each job gets its own temp dir.
- `JsonlStore.upsert` rewrites the whole file with no lock. It is O(N) per write and loses updates under concurrent writers. It is currently used only by CLI and batch paths.
- `probe_video` decodes the entire stream before applying the duration limit, so a 500 MB file is fully decoded before it is rejected.
- About 2,300 lines of duplicate pipeline code (`oldversion/`, `notebooks/CVmodel_export.py`).

## 3. What is sound (credit where due, V-code)

- **Contracts and provenance:** strict Pydantic schemas (`extra="forbid"`), a version-plus-config digest in every cache key, input checksums, measurements mapped back to original-image pixels through letterbox geometry, and RFC-7807-style error codes.
- **Epistemic labelling:** explicit OBSERVED/MEASURED/ESTIMATED labels, a "no temperature from RGB" warning on every result, and `confidenceBasis: "heuristic_uncalibrated"`.
- **Input hardening:** size, pixel-count and decompression-bomb limits, a format allow-list, a codec allow-list for video, and Pillow ≥ 13 for decoder CVEs.
- **Video engineering:** content-addressed IDs, VFR-to-CFR resampling without interpolation, resumable JSONL and PostgreSQL checkpoints with a job digest, and cancellation.
- **Temporal guards:** flicker is refused below Nyquist, on short runs or without a dominant peak; tracking is withheld when sampling is too sparse.
- **`video_training.py` protocol:** group-wise LOTO, nested regularisation and a baseline for every task.

The engineering around the model is strong. The weak points are what the model detects and how that was checked.

## 4. Current approach vs alternatives

| Need | Current | Better fit for this data | Why |
|---|---|---|---|
| Exclude overlays and hardware | None in the served path | Static ROI mask per camera, plus temporal-static-component rejection | Fixes CV-1 cheaply; no learning needed |
| Flame vs bright clutter | Global Otsu + brightness score | Colour/chromaticity gating (soot-luminous orange vs blue/white), background subtraction from pre-ignition frames | Every BASS-II and SPICE video has pre-ignition frames: a free background model |
| Segmentation quality | Unmeasured | Small labelled set (CV-3), then a light U-Net or a fine-tuned promptable segmenter if heuristics plateau | Labels first; no model choice is meaningful without them |
| Temporal | Independent per-frame Otsu | Per-video threshold or hysteresis, plus a simple tracker | Removes threshold jitter from area signals |
| Physical outputs (spread rate, extinction time) | Not attempted | Leading-edge position vs time from masks, with the scale from `mmPerPixel` | This is the BASS-II gap named in `FINAL_PROJECT_STATUS.md:41` and `FINAL_CHALLENGE_PRESENTATION.md:106` |
| Learned video features | ResNet on 17 videos | Keep it frozen; add permutation tests; only after CV-1 is fixed, use OCR-derived labels | n is far too small for end-to-end CNN or LSTM training |
